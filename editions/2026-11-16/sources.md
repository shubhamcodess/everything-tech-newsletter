## [1] All AI-generated code should be Open Source
Hacker News | full text via Hacker News | ~310 words

All AI-generated code should be Open Source
This may be a hot take, but I strongly believe that all code generated by AI should be Open Source. And here's why.
First of all, AI models were trained on a massive corpus of Open Source code written since RMS announced the GNU Project and the Free Software Movement. That code was simply scraped from the internet and used without permission or proper attribution. The models were also trained on Stack Overflow and Stack Exchange sister projects, which are released under Creative Commons licenses that legally require attribution. Turning this collective knowledge into proprietary, closed-source code feels like license laundering.
The second reason is legal: purely AI-generated code is not written by a human, meaning it should not be copyrightable. The foundation for this principle in the US goes back to the famous Monkey Selfie dispute, which established that non-humans cannot hold copyrights. A precedent later cited by the U.S. Copyright Office regarding AI. Following the same logic, Wikimedia Commons requires all purely AI-generated images to be tagged as Public Domain.
However, copyright laws differ across the globe. For instance, countries like the UK grant limited copyright protection to computer-generated works. To make things fair across all jurisdictions, and to honor the open ecosystem that made AI possible, developers and companies should explicitly release AI-generated code under Open Source licenses or dedicate it to the public domain using the Creative Commons Zero (CC0) license.
Of course, code is not always 100% manual or 100% automated. However, developers more and more rely on AI without even reviewing the generated output, let alone modifying it to fit their specific needs. Code like this, where humans put little effort, except writing prompts, should definitely be Open Source.

## [25] Anthropic Outlines its AI-Powered Code Review Process for Claude Code
InfoQ | full text via InfoQ | ~486 words

Anthropic has outlined how the Claude Code team handles code reviews as AI agents increasingly contribute to its codebase. The approach relies on multiple layers of automated verification, AI-powered reviews, and risk-based human approval, aiming to reduce manual review time without increasing regressions or production incidents.
Addy Osmani, Morgan Westlee Lunt and Qing Wang described how the team's review process has evolved alongside the growing volume of AI-generated code. Between June and September, merged pull requests to the Claude Code repository more than doubled, while the proportion of changes requiring a revert fell by over 40%.
Rather than relying on traditional line-by-line reviews, the team has moved much of the verification earlier in the development process. Before opening a pull request, Claude runs tests, builds, and linters, while a separate agent reviews the changes in a fresh context.
Every pull request then goes through several automated checks. Claude-powered reviewers inspect code changes for potential bugs, with multiple agents independently investigating findings before another group verifies them. A separate security review can also block a merge if unresolved issues remain.
This approach also raises questions about the evolving boundaries between software engineering, testing, and quality assurance. As one commenter put it:
So code review is officially synonymous with testing now? Should the code review mechanism be owned by QA team? Is there still a QA team?
Human involvement depends on the risk associated with a change. Low-risk modifications, such as documentation updates or internal features behind feature flags, may require no human approval. Medium-risk changes require one person, while high-risk modifications need two approvals. Changes to particularly sensitive areas, including CI workflows, always require human oversight.
The team also introduced mechanisms to prevent automated reviews from generating excessive feedback. Review cycles are capped at three rounds before the author is asked to reconsider the implementation. Subsequent reviews focus on new changes rather than repeatedly examining the entire pull request.
These adjustments have improved review efficiency. According to Anthropic, the share of internal pull requests passing after one review and fix round increased from 65% to 78%. Meanwhile, the proportion requiring five or more rounds dropped from 8.9% to 1.5%.

## [21] Uber's Secure AI Framework Governs Autonomous AI Agents across Their Lifecycle
InfoQ | full text via InfoQ | ~593 words

In a recent article, Uber Engineering highlights the limitations of traditional identity and API controls in securing AI agents that dynamically reason over external content and take real-world actions. To address this challenge, Uber developed a framework to determine whether an agent's action is appropriate given the user's request, the agent's intended purpose, its permissions, and the context of the interaction.
Identity and authorization systems can determine whether a user or service has permission to access a resource, but they can't determine whether an agent's proposed action is appropriate in context.
This creates multiple risks, including prompt injection, tool and memory poisoning, goal hijacking, behavioral drift, and hallucination-driven actions, which Uber's framework addresses through three layers spanning the entire agent lifecycle, from pre-deployment to runtime enforcement to post-deployment continuous assurance.
At provisioning time, agents must be registered in the Uber AI Registry, establishing identity, ownership, persona, permitted intents, constraints, dependencies, and risk classification. This process is automated using Argus, which analyzes the agent's source code, prompts, configurations, dependencies, exposed endpoints, and tool-invocation paths to identify security weaknesses. The same approach is enforced for MCP servers and tools used by the agents.
At runtime, the framework extends the traditional security model based on policy administration, policy decision, and policy enforcement to incorporate behavioral authorization, which evaluates whether an agent's actions are appropriate in a given context.
Behavioral authorization is implemented through three components: the AI Registry, AI guards, and Agent Guard runtime hooks. The AI Registry defines and manages agent policies, personas, intents, and constraints, while AI Guards evaluate interactions and proposed actions against established policies. Agent Guard runtime hooks invoke AI Guard "at critical checkpoints and applying its verdict before an interaction or action is allowed to proceed".
After deployment, the focus shifts to Continuous Assurance, which relies on end-to-end observability, auditing, explainability, and replay. This layer comprises two main main components: a unified execution trace that connects agent actions, tool calls, and security decisions; and recorded interactions that can be replayed whenever policies and guardrails are updated to assess their effectiveness in the new context. ## [28] FreeBSD bhyve Live Migration: Moving VMs Between Hosts
Lobsters | full text via Lobsters | ~1230 words

This project presents a first working state for live migration of bhyve guests on FreeBSD 15.1. A running amd64 guest can move between two hosts over TCP while continuing to run; it is paused only for the final stop-and-copy phase. The work builds on bhyve's experimental snapshot support and adds dirty-page tracking in the vmm kernel module together with a migration protocol in bhyve and bhyvectl.
I previously discussed the state of bhyve live migration, its historical development, existing limitations, and why it matters for the future of FreeBSD virtualization in my article bhyve on FreeBSD and VM Live Migration – Quo vadis?.
The goal is deliberately practical: make it possible to test, discuss, and improve a real implementation rather than discuss live migration only in the abstract. The current code and test tooling are being published as a WIP RFC so that the next steps can be shaped in the open. A more detailed demonstration of a VM being live migrated can be watched on my YouTube channel.
Why this matters
Live migration is an important building block for enterprise virtualisation. It enables host maintenance, hardware replacement, load balancing, and failure-domain management with far less disruption to workloads. It is also central to the Sylve project, which aims to offer a Proxmox-like virtualisation solution for FreeBSD. Migration is not an optional convenience in that kind of platform; it is one of the capabilities that makes clustered operations practical.
It is equally important for BoxyBSD, where I offer free BSD-based VPS instances to individuals. Without a credible migration path, routine host work can require a guest outage. That makes live migration a current show stopper for the project, and is why this work is being pushed toward a testable, reviewable state.
How the current implementation works
The source starts with a pre-copy phase. It sends populated guest memory, then repeatedly obtains a bitmap of pages changed since the previous scan and sends only those pages. Once the remaining dirty set fits the configured downtime target, stops shrinking, or reaches the configured round limit, bhyve pauses the guest and its devices. It then sends the final dirty pages and the existing snapshot state for the vCPUs, kernel state, and emulated devices.
The destination validates the basic VM geometry, receives memory and state, restores it, and reports that it is ready. Only then does the source send GO, the commit point. Before GO, a failed migration can resume the source guest. The destination does not start the guest if it does not receive that commit message.
