## [22] Meta Brings Code Review Auto-Approval More Mainstream with PyTorch GreenLight
InfoQ | full text via InfoQ | ~860 words

GreenLight has started letting a PyTorch AI reviewer approve pull requests from its own maintainers. It is an open-source take on RADAR, the system Meta uses to land low-risk code changes without waiting on a human. The move comes as Meta, OpenAI, Anthropic and Sonar all describe ways to automate approval itself.
RADAR stands for Risk Aware Diff Auto Review. Meta described it in a paper published in May. The paper starts from a capacity problem. Significant lines of code per human-landed diff rose 105.9% year over year, and diffs per developer per month rose 51%.
Meta attributes more than 80% of that increase to agentic AI assistance. Review has not kept pace, and the share of diffs reviewed within 24 hours is dropping. The authors describe their response in narrow terms.
Rather than attempting to replace code review broadly, RADAR targets automation to diffs that satisfy conservative safety criteria.
RADAR sorts each diff by author and source before anything else. Deterministic codemods can be approved through a blanket policy and skip per-diff AI review. AI-generated codemods and automated runbooks go through a pipeline of safety checks, a Diff Risk Score and an LLM reviewer. Any failure sends the diff to a human.
RADAR pipeline for AI and bot diffs. Source: Meta, "Automating Low-Risk Code Review at Meta" (arXiv 2605.30208)
The safety checks are hard limits. Open-source code, SOX-scoped code and code that needs extra review are never eligible. Runbooks must show a clean 60-day record, with zero production incidents and low revert and rejection rates. They are also capped at up to 2,000 diffs per day.
The Diff Risk Score works as a percentile gate. Allowlisted runbooks can land diffs up to the 50th percentile of risk. Other AI and bot sources stop at the 20th. Human-authored diffs default to the 5th, and each organization can tune its own thresholds.
The last gate is the RADAR Review Agent, which reads the actual change. It looks for safe patterns such as dead code removal, refactoring without behavior change, logging additions and new tests. The paper sets a strict bar for the agent.
For a diff to be auto-accepted, ACR requires a confidence score of at least 8 out of 10, with all changes classified into safe categories.

## [23] Netflix Builds Quasar to Measure the Blast Radius of Library API Changes
InfoQ | full text via InfoQ | ~474 words

Netflix has developed Quasar, an internal tool that identifies which repositories use specific library API symbols, helping engineering teams assess the downstream impact of proposed changes before releasing them. The tool combines semantic code indexing with API comparisons to identify affected consumers, dependency versions, and relevant call sites across repositories.
The challenge extends beyond identifying whether an API change is incompatible. Compatibility tools can flag a removed method or changed signature, but they do not necessarily identify which applications call it. Dependency graphs show declared relationships rather than actual usage, while text searches can miss references involving inheritance, overloads, and generated code. Building every downstream consumer to validate a change can also be expensive.
Quasar architecture diagram showing the indexing and query workflow (Source: Netflix Blog Post)
Quasar indexes symbol definitions and references using the SCIP Code Intelligence Protocol, an open format for representing code relationships. Language-specific indexers submit data during CI builds, which Quasar stores in Amazon S3 as Parquet files and queries through Amazon Athena.
During pull request analysis, Quasar compares API definitions between commits and identifies added, removed, or modified symbols. It then queries indexed references to locate affected repositories, dependency versions, and source locations. A Netflix example shows a deprecated method removal affecting 137 repositories across three library versions.
Example Quasar impact report showing affected repositories and dependency versions (Source: Netflix Blog Post)
However, an absence of indexed references does not prove that an API is unused. Reflection, dynamic loading, stale indexes, and incomplete coverage can prevent Quasar from observing every consumer.

It's also good for synchronizing an existing copy of a database without re-transmitting the entire thing over the network. It works in a similar way to regular rsync:
The core idea behind the protocol is that the replica sends cryptographic hashes for pages or groups of pages over to the origin side. The origin sends back page content that differs, or requests finer-grain hashes if a multi-page hash does not match. If the origin and replica start out being vastly different, the total network bandwidth can exceed the size of the entire database, due to the overhead of exchanging hashes, but the excess bandwidth is not great - a few percent at most.

rust 2026-11-24
It's only been a couple of months since the last article, and I am pleased to see that, after 10 years of limbo, allocators have finally been stabilised! So, now we have an MVP of the allocator API, what can we do with it? What does it get us besides closer feature parity with other system languages like C++ & Zig?
In this article I'll step through a few use cases that might be handy to the layman rust programmer, so hopefully you can see the benefit.
Allocators can adjust when memory is freed
This was one of the leading cases for custom allocation. Dropping in rust is not free. There has been prior art in actually moving memory to a dedicated thread to Drop highly nested structures. This is actually only half a solution. You're still paying for the deallocation call costs, just it's not in the hot path anymore.
Instead, what if we knew that we would have a period of time in our code, where we're going to allocate a lot of stuff, do something with it, and then free everything? A good example of this is a web request, or a database query.
A request comes in, fills in some data structures, and then when the request finishes, the memory isn't needed anymore so it's dropped. This sort of "burst" pattern of allocation, where you allocate a lot up front, and then tear things down all at once at the end, is quite common.
For this we can use a bump allocator: reserve a big block of memory, and allocate from that, rather than paying the cost of talking to the system allocator for every allocation. Think of it like the BufReader and BufWriter of std io, rather than make repeated syscalls to fetch data, we can buffer that data in a big block, so that we can reduce the overhead considerably.
You want more memory? Just check if the size fits in our block, return that slice, increment our counter (bump!), and we're done. We can add more blocks as well, if we run out. This makes allocations very cheap, we don't need to keep much state around besides from a counter.

It was first introduced in Vite 2.7 and had been improved over the years. The check was a block-list based approach where you and Vite needed to list the sensitive files. This made sense initially as one of Vite's feature is to have implicit entrypoints.
Due to the nature of the block-list approach, we have to fix the bypasses exploiting the quirks of the file system, HTTP parsing. While we had been patching the block-list approach for less breakage in the ecosystem, given that the number of attacks are increasing, Vite 8.4 introduces a stricter allow-list based check. server.fs.strict: 'extended' was added to also apply the checks to modules loaded by plugins, and Vite now registers the referenced modules in the allow list not only via import but also via other ways such as url() in CSS.
Combining server.fs.strict: 'extended' with server.fs.allow: [], you can now opt in to the allow-list based approach. This will only allow the files referenced from the entrypoint, including the transitive references. We intend to switch to this approach by default in the next major.
If a plugin generates a module that references an asset not by import, it can call this.environment.addSafeModule so that users don't need to add the referenced module in server.fs.allow.
