A flaw in Broadcom's Wi-Fi software dating back to at least 2010 lets anyone within radio range take over a vulnerable router without its password, and the fix Broadcom says it shipped years ago never reached many routers that need it.
Security researcher Quentin Kaiser presented the bug at the recent Hexacon event alongside a detailed write-up, naming it 'WPSplinter', a name he admits to disliking; with no CVE assigned, it is the only label the flaw has.
The bug sits in Broadcom's legacy WPS Monitor, the component that handles Wi-Fi Protected Setup, the push-button pairing feature found on many home routers. When WPS messages arrive in fragments, the software stitches them back together without checking that the result fits in the memory set aside for it.
No password, no pairing, no problem?
According to Kaiser's public documentation page, an attacker can reach that code over the air before any pairing completes, so no PIN, no button press and no network key are required. The upshot: anyone in range can read the router's memory and run code on it. Unlike the WPS PIN brute-forcing attacks of the early 2010s, the weakness is in Broadcom's code, not the protocol itself.
On an Askey TCG3000 gateway supplied by Orange Belgium, Kaiser's code pulled the Wi-Fi password from the router's storage and sent it over the air; he then used it to join the network. On a Sagemcom-built Proximus BBOX3V+, he opened a remote shell running entirely over Wi-Fi frames. He says the attack works at long range, though he has not published a distance. ## [53] MCP C# SDK 2.0 Makes HTTP Stateless by Default and Adds Multi Round-Trip Requests
InfoQ | full text via InfoQ | ~593 words

Microsoft announced the stable release of version 2.0 of the official MCP C# SDK, implementing the 2026-07-28 revision of the Model Context Protocol (MCP) specification. The release makes Streamable HTTP servers stateless by default, standardises HTTP headers so infrastructure can route MCP traffic, and introduces Multi Round-Trip Requests (MRTR) for interactive tools. Three minor releases, 2.1 to 2.3, followed between August and October.
MCP is an open protocol that standardises how applications supply context and tools to large language models. The C# SDK is maintained in collaboration with Microsoft and builds on ASP.NET Core. The SDK team describes the new specification revision as the largest since the protocol launched, because it rethinks how MCP works over HTTP.
The initialize handshake and the Mcp-Session-Id header are gone. Protocol version and capabilities now travel with every request, so any server instance can handle any request without sticky routing or shared session stores. HttpServerTransportOptions.Stateless now defaults to true; servers that need sessions set it to false. Clients probe server/discover first and fall back to the legacy handshake for older servers. Stateful-only options and the legacy SSE endpoints now raise MCP9006 and MCP9004 warnings.
A tools/call request now carries Mcp-Method and Mcp-Name headers, and the [McpHeader] attribute promotes a tool parameter to an Mcp-Param-* header. Load balancers and gateways can then route on headers without reading the body. The body stays authoritative: a mismatched header makes the server return a HeaderMismatch error.
Statelessness removes the channel servers used to ask clients for input mid-call. MRTR replaces it: a tool throws InputRequiredException with one or more input requests, built with InputRequest.ForElicitation, ForSampling or ForRootsList, plus an opaque requestState. The client collects the answers and re-issues the call with inputResponses. McpClient does this automatically when handlers are registered. Over stateful sessions with 2025-11-25 or earlier clients, the SDK bridges to the old server-initiated requests; on stateless down-level connections the request surfaces as an McpException. Roots, sampling and logging APIs are deprecated under MCP9005, following SEP-2577.

I'm more and more convinced that a staff of always-on agents is the right way to work. It's a really good idea, for reasons I'll talk about below. And GrokBot is the closest thing we have to a working implementation. But it's just not there yet, and the reasons are architectural.
Why I wanted a staff in the first place
Coding agents can already do a lot of the work. What wears me out is everything around it: knowing which PRs are waiting on review, what came in overnight, and what to work on next. I wanted to engineer that mental load off me and into the system.
GrokBot is built for exactly that. Each bot is an agent with its own chat and its own little Linux computer in the cloud, and with the desktop app installed, it can run commands on your machines too. Bots run routines on a schedule or when a webhook fires, and they can even reconfigure each other.
So I hired 16 of them, one per area of my work: Inbox, GitHub, Bugs, Blog, Research and so on. A Config bot's whole job was setting up the others, and a Vault bot was the only one allowed to write to my notes.
When a project needed a few bots at once, I'd pull them into a group chat: "Okay, in this room we're only working on this project."
Then I connected them to my coding. I write code in T3 Code, a desktop app that runs Claude Code and Codex threads side by side, because that's where my Anthropic and Codex subscriptions and the models I like live.
I didn't want to open T3 to the cloud through a public tunnel, where anyone with the URL, or a bot with a prompt injection in its context, could run commands on my PC. So a small script on my PC, no AI involved, pinged a GrokBot webhook whenever a coding thread finished, failed, or needed me. That woke my T3 Code bot, which could tell me about it or act back on my PC through the desktop app. [...]
